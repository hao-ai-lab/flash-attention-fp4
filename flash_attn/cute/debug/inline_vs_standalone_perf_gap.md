# Inline vs Standalone FP4 Kernel Performance Gap

## Summary

The inline block-scaled kernel in `flash_fwd_sm100.py` (flash_attn_pr) achieves **1634 TF** for NVFP4+BF16 on (1,32768,24,128), vs **1793 TF** for the standalone `flash_fwd_sm100_fp4.py` (fp4-rebase). The **9% gap** is from extra BAR.SYNC/BAR.ARV instructions generated by the pipeline API.

## SASS Comparison

| Metric | Inline | Standalone |
|--------|--------|-----------|
| Total SASS instructions | 3416 | 3739 |
| Cubin size | 95 KB | 106 KB |
| BAR.SYNC | **11** | **1** |
| BAR.ARV | **5** | **0** |
| ELECT | 12 | 8 |
| UTCBAR | 12 | 12 |

Standalone has more total instructions but **10 fewer BAR.SYNC and 5 fewer BAR.ARV**. BAR.SYNC is a warp-level synchronization (all threads must reach it); BAR.ARV is a named barrier arrive. Both stall the pipeline. UTCBAR (`tcgen05.commit`) and MBAR.ARRIVE are non-blocking.

## Root Cause: `elect_one()` Warp Reconvergence

The `pipeline_s_p_o.producer_acquire` (used before PV gemm) calls `sync_object_full.arrive()` → `arrive_tcgen05mma()` → `elect_one() + tcgen05.commit()`. The `elect_one()` generates:

```
ELECT P0, URZ, PT    ; one thread wins
@P0 UTCBAR [mbar]    ; winner commits
BAR.SYNC 0x2, 0x1a0  ; all threads reconverge  ← THIS IS THE OVERHEAD
```

The standalone uses the identical `elect_one() + tcgen05.commit()` pattern but ptxas **optimizes away the BAR.SYNC reconvergence** for the standalone while keeping it for the inline. This is because ptxas's reconvergence optimization depends on the surrounding code's control flow graph complexity.

## Why ptxas Optimizes Standalone But Not Inline

The standalone kernel generates a simpler control flow graph:
- Only block-scaled code paths (no non-FP4 branches)
- Raw mbarrier operations (flat barrier graph)
- Single-purpose warp scheduling

The inline kernel's control flow graph includes:
- `const_expr` branches for block_scaled_qk vs non-block-scaled paths
- Pipeline API wrappers that add layers of method dispatch
- Named barriers (sm_stats_barrier) alongside pipeline mbarriers
- Multiple pipeline instances (pipeline_s_p_o, pipeline_p_lastsplit, pipeline_o_acc, pipeline_sm_stats, pipeline_s0_s1_sequence, pipeline_q, pipeline_kv)

ptxas's warp reconvergence pass works by proving that threads will reconverge naturally at a subsequent control flow join point. In the standalone, the code after `elect_one` is simple enough that ptxas can prove reconvergence without inserting BAR.SYNC. In the inline, the surrounding pipeline API code prevents this proof.

## Why Adding Raw Mbarriers Causes ptxas to Hang

When we tried replacing `pipeline_s_p_o` with raw `mbarrier_wait` / `tcgen05.commit` / `mbarrier_arrive` for the block-scaled path:
- Both with `elect_one()` and without caused ptxas to run for 30+ minutes before being killed
- The inline kernel compiles in ~7 seconds without the raw mbarrier changes

This is **NOT** because raw mbarriers are inherently slow to compile — the standalone (which uses only raw mbarriers) compiles in 6 seconds. The issue is the **coexistence** of the pipeline API's barrier operations AND raw mbarrier operations in the same kernel.

ptxas performs global barrier graph analysis to optimize synchronization. When both the pipeline's `PipelineUmmaAsync` barriers (which use specific patterns of `tcgen05.commit`, `mbarrier_wait`, `mbarrier_arrive`) and separate raw mbarrier operations exist in the same kernel, ptxas's barrier graph optimizer faces a combinatorial explosion:
- The pipeline barriers have implicit ordering constraints from the producer/consumer API
- The raw mbarriers have independent ordering constraints
- ptxas tries to prove safety of all possible interleavings → exponential complexity

The standalone avoids this because ALL its barriers are raw mbarriers with a simple, flat dependency graph that ptxas can analyze efficiently.

### Why a clean `const_expr` if/else doesn't help

Even with `const_expr(self.block_scaled_qk)` guarding the raw mbarrier path, ptxas still sees both code paths during compilation. The `const_expr` eliminates dead code at the DSL IR level, but the PTX generated for the live path still contains BOTH:
- Pipeline API barrier operations from `pipeline_s_p_o.producer_acquire` (in the PV gemm path, which is shared between block-scaled and non-block-scaled)
- Raw mbarrier operations from the block-scaled S2T/QK path

The PV gemm's `producer_acquire` uses `pipeline_s_p_o` regardless of `block_scaled_qk` because P/O coordination still needs the pipeline. The QK S2T uses raw mbarriers. This mix is what triggers ptxas's pathological behavior.

To have a truly clean separation, we'd need to replace ALL `pipeline_s_p_o` operations with raw mbarriers for block-scaled — including the PV gemm P/O coordination. But that requires reimplementing the full pipeline protocol (S commit, P-ready wait, O-rescale signal, correction warp coordination) with raw mbarriers, which is essentially writing a separate kernel.

## Would CUDA 13 ptxas Help?

Possibly, for two reasons:

1. **Improved warp reconvergence optimization**: CUDA 13 may have a newer reconvergence pass that can prove thread convergence in more complex control flow graphs, eliminating the extra BAR.SYNC for the inline kernel's `elect_one()` blocks.

2. **Better barrier graph analysis**: CUDA 13's ptxas may handle mixed barrier graphs (pipeline API + raw mbarriers) without the exponential blowup, allowing the raw mbarrier approach to compile in reasonable time.

However, this is speculative — NVIDIA doesn't document ptxas optimization improvements in detail. The CUDA 12.9 ptxas was built May 2025; a newer version may or may not address these specific limitations.

**How to test**: Install `nvidia-cuda-nvcc` for CUDA 13.x (currently unavailable as a pip package — the `nvidia-cuda-nvcc>=13` package installs but ships the same 12.9 binary). Would need CUDA Toolkit 13.x installed from NVIDIA's deb/rpm repos, then set `CUTE_DSL_PTXAS_PATH` to the new binary.

## What Was Fixed (+14%)

Removed `pipeline_s_p_o.sync_object_empty.wait()` for S2T SF copy coordination. This wait created a false dependency on the full P-write + O-rescale pipeline, stalling the MMA warp unnecessarily.

Commit: `5f41dac7`

## Updated Analysis: IPC Gap, Not BAR.SYNC

Detailed ncu profiling reveals the gap is from **8% lower IPC** (1.72 vs 1.87 inst/cycle), not directly from BAR.SYNC count:

| Metric | Inline | Standalone | Delta |
|--------|--------|-----------|-------|
| Time | 12.49 ms | 11.11 ms | +12.4% |
| Instructions | 3,617M | 3,490M | +3.6% |
| IPC | 1.72 | 1.87 | **-8.0%** |
| SM throughput | 67.57% | 76.20% | **-8.6 pp** |
| Active warps | 16 | 16 | same |

Only 2 of the 11 BAR.SYNC are in the MMA hot loop (at 0x3120 and 0x4730). At ~20 cycles each × 256 iterations = 10K cycles out of 24M total — only 0.04% overhead. The remaining BAR.SYNC are in softmax/correction warps (not on the critical MMA path).

The 8% IPC gap is from **ptxas instruction scheduling quality**:
- The inline kernel's more complex PTX (pipeline API wrappers, const_expr branches, named barriers alongside mbarriers) produces instruction schedules with more pipeline stalls
- The standalone's simpler PTX (raw mbarrier operations only) allows ptxas to produce tighter instruction scheduling
- Same active warp count (16) means the stalls aren't from occupancy — they're from instruction-level dependencies

This is a ptxas code generation quality issue that cannot be fixed by changing barrier types. The inline kernel's code structure inherently produces worse scheduling due to the abstraction layers.
